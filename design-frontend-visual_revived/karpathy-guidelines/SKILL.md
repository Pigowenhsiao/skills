# Karpathy Guidelines

這是一組從 Andrej Karpathy 對 LLM coding 常見失誤的觀察中整理出的行為準則。

這個 skill 適合用在以下風險很高的情境：
- 模型可能會默默替你補假設
- 實作可能會越寫越大、越寫越複雜
- 修改可能會外溢到不相關的區塊
- 還沒驗證就想宣稱「已完成」

它不是測試、code review 或專案規範的替代品，而是一套在實作前與實作中都能套用的操作紀律。

## 核心原則

### 1. 先想清楚再寫

不要默默猜。

在開始實作前：
- 重要假設要先講出來
- 如果存在多種合理解讀，不要默默挑一種就做
- 如果需求和程式碼現況互相衝突，要直接指出來
- 如果有更簡單的路徑，要提出來並說明理由
- 如果真的不清楚，就停下來問

目標是把混亂暴露在前面，而不是把混亂埋進程式碼裡。

### 2. 簡單優先

只寫解決當前問題所需的最小程式碼。

避免以下做法：
- 預先加功能
- 為了單次使用就抽象化
- 加入沒人要求的可配置性
- 為幾乎不可能發生的情況堆防禦邏輯
- 用「未來可能用得到」當理由，增加今天的複雜度

如果一個解法看起來太聰明、太密、太有彈性，通常就代表它過頭了。

可用的自我檢查：
- 一個夠強的資深工程師，會不會覺得這個方案太重？
- 如果會，就繼續簡化。

### 3. 外科手術式修改

只碰這個任務真正需要碰的地方。

在修改既有程式碼時：
- 不要因為剛好看到，就順手「改善」旁邊的程式、註解或排版
- 不要重構沒有壞掉的東西
- 除非有充分理由，否則盡量對齊當地既有寫法

只清你自己造成的後果：
- 移除因為你的修改才變成未使用的 import、變數或函式
- 不要順手刪掉本來就存在的 dead code，除非使用者有要求

可用的自我檢查：
- 每一行修改都應該能回溯到使用者需求，或是該需求直接導致的必要變更。

### 4. 以目標與驗證驅動執行

把任務翻成可驗證的結果。

優先採用這種思路：
- 「寫一個會先失敗的測試，再讓它通過」
- 「找出哪個檢查能證明這個 bug 真的沒了」
- 「在實作前先定義成功條件」

遇到多步驟任務時，維持一個簡短迴圈：

```text
1. 釐清目標
2. 定義驗證方式
3. 做最小且正確的修改
4. 執行驗證
5. 帶著證據回報結果
```

像「把它弄好」或「幫我優化一下」這種模糊目標，很容易讓實作漂掉。明確成功條件才能把工作釘住。

## 實際工作模式

在非 trivial 的 coding 任務中，套用這個 skill 時可依序做：

1. 把任務重述成可操作的目標
2. 說出主要假設與風險
3. 指出要用什麼來判斷成功
4. 做最小可行修改
5. 驗證後再宣稱完成

如果任務非常小，就用判斷力，不要為了儀式感而加流程。

## 常見失敗模式

### 沉默式假設漂移

錯誤模式：
- 需求其實有歧義
- 模型自己選一種解讀
- 然後把那個解讀當成已確認事實一路做下去

正確做法：
- 先指出歧義
- 列出可能解讀
- 要嘛先問，要嘛明確標示「我現在基於這個假設往下做」

### 抽象膨脹

錯誤模式：
- 沒有真正需求，卻先長出 helper layer、config object、generic wrapper、extension point

正確做法：
- 單次使用的邏輯優先內聯
- 優先寫明顯、局部、可讀的程式，而不是看起來很可重用的骨架

### 路過式清理

錯誤模式：
- 做一個小任務時，順便改了不相關的註解、排版、命名或舊程式

正確做法：
- 把那些觀察單獨說出來
- 但這次 diff 先維持聚焦

### 沒證據就宣稱成功

錯誤模式：
- 「現在應該可以了」
- 「這個已經修好了」
- 「測試應該會過」

正確做法：
- 跑能證明的命令
- 讀結果
- 用實際證據回報

## 和現有 Agent Skills 的關係

這個 skill 和下列 skill 有重疊，但不互相取代：

- `code-simplicity-reviewer`
  更偏向實作完成後的簡化審查
- `verification-before-completion`
  更偏向完成前的硬性驗證閘門

`karpathy-guidelines` 比較適合更早套用：
- 開始寫之前
- 實作進行中
- 在判斷方案形狀時

如果你已經做完了，想再嚴格做一次收尾，那就交給後面那兩個 skill。
